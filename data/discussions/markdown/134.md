## **Summary**

This is a technical RFC that proposes updates to the Additional FedRAMP Security Technical Controls Requirements and Guidance for FedRAMP Rev5 baselines.

To save space and to limit the breadth of a single RFC, this technical document shows only the proposed changes to the current baseline document and is restricted to a few control families.  If verbiage is being updated, only the specific wording that is to be changed is identified in the old verbiage section.  If the verbiage to be added is not replacing previous verbiage, but being added, it will be identified as “NEW” in the old verbiage section.  

Since this spreadsheet covers hundreds of controls across multiple tabs and sections, only those specific controls, sections, and tabs identified are being proposed for updates. If it is not mentioned below, changes are **not** being proposed.  

**Commenters are advised to please mention specific controls in their comments!**

This RFC addresses controls in the following families:

* Risk Assessment (RA)  
* System and Service Acquisition (SA)  
* System and Communications Protection (SC)  
* System and Information Integrity (SI)  
* Supply Chain Risk Management (SR)

## **Motivation**

Many Rev5 FedRAMP Requirements and Guidance statements are based on outdated approaches that predated the release of the FedRAMP Authorization Act and M-24-15. This set of Requirements and Guidance needs a refresh to match FedRAMP’s current rules and approach.

The updates formalized after this RFC will be included in the FedRAMP Consolidated Rules for 2026. That set of rules will be valid until December 31, 2028. FedRAMP will provide a transition plan for adopting any new guidance that will enable cloud service providers to update their approach as part of their annual assessment as appropriate.

These changes are designed to lower the burden for cloud service providers and eliminate previous pain points.

Additionally, NIST released 800-53 Rev 5.2.0 in August of 2025. While this update was minor, control updates from NIST will require updates to FedRAMP Security Control Baseline in order to reflect this update. These changes will happen without public comment through FedRAMP since these are direct reflections of NIST changes.  As subsequent iterations of the FedRAMP Security Control Baseline are published, it is FedRAMP’s intent only to carry over the following information from NIST 800-53: Control Family, Control Name, and Control ID. Following this will be FedRAMP-Defined Assignment / Selection Parameters and additional FedRAMP Requirements and Guidance.

### RA-5 (Vulnerability Monitoring and Scanning)

**What works**

- Splitting **traditional monthly scanning + 30/90/180** from VDR-based frequencies and VDR mitigation logic is helpful.

**Suggestions**

- Clarify what “representative samples of similar machine-based information resources” means operationally:
  - minimum sampling rate or statistical approach,
  - how “similar” is determined (e.g., image lineage, config profile, role, exposure),
  - how the CSP proves the sample remains representative as the environment changes.
- “Evaluate ALL vulnerabilities within X days of detection” is strong and useful, but it would help to specify whether “evaluate” means:
  - triage + impact determination,
  - exploitability/reachability determination,
  - assignment of remediation timeline category,
  - and/or documented acceptance/false-positive disposition.
- Confirm how **KEV supersedence** applies under VDR (i.e., does KEV always override VDR timelines, or is it incorporated into VDR’s categorization?).

### SA-4(5) (Config baselines)

**Suggestion**

- Consider requiring documentation to include:
  - rationale for deviations from STIG/CIS,
  - mapping to control objectives,
  - and a repeatable validation method (so 3PAOs can assess consistently).

### SA-5 (System Documentation)

**Concern**

- The proposed parameter “a. (1) in conjunction with the FedRAMP Security Configuration Guidance” is directionally good, but feels incomplete as written (it’s hard to implement or test as a standalone parameter).

**Suggestion**

- Consider explicitly stating what documentation artifacts are required “in conjunction with” SCG (e.g., configuration baseline artifacts, implementation evidence, or update cadence).

### SA-15 (Authorization/Certification wording)

**Suggestion**

- Ensure consistent use across all baselines and templates to avoid mismatched language in SSP/SAR/POA&M narratives.

### SC-7(5) (Deny by default—allow by exception)

**Suggestion**

- Consider explicitly acknowledging typical cloud constructs (“services,” managed control planes, serverless) so CSPs don’t get pushed into artificial “system” mappings.

### SC-7(8) (Authenticated proxy routing) – MAS vs traditional

**Suggestion**

- The bracketed phrase appears to have an unmatched parenthesis in the proposed change; recommend tightening the grammar and explicitly defining what counts as:
  - “outside of assessment scope” under MAS, and
  - “outside the established boundary” under traditional,
     to reduce 3PAO interpretation risk.

### SC-13 (Cryptographic modules in CMVP “historical” status)

**Suggestion**

- Add explicit expectations:
  - what evidence must be provided when a module becomes “historical,”
  - expected timelines or triggers for transition/remediation,
  - how FedRAMP will treat “historical” status during annual assessments vs significant changes.

### SI-2(2), SI-3 (shift to “persistently” for VDR participants)

**Suggestion**

- Define the minimum acceptable evidence of “persistent” (e.g., continuous telemetry + alerting, near-real-time status reporting) so CSPs don’t overbuild and 3PAOs don’t under-test.

### SI-5 (EDs/BODs via FedRAMP Secure Inbox)

**Suggestion**

- Add clarity on:
  - whether timelines are driven by the directive itself or FSI guidance (or both),
  - whether CSPs must maintain a standing ED/BOD tracker artifact and where it lives (SSP appendix vs ConMon deliverable).

### SI-8 (DMARC link update)

**Suggestion**

- Consider a short note about scope:
  - applies when sending email “on behalf of the government,”
  - and whether subdomains / third-party senders used by the CSO must also meet policy=reject + reporting requirements.

## vedigaurav — [2026-04-05T02:22:09Z](https://github.com/FedRAMP/community/discussions/134#discussioncomment-16451741)

Gap #1 – Insufficient alignment with threat-informed defense practices
Issue: While RFC-0030 updates controls across RA, SA, SC, SI, and SR families, it does not explicitly incorporate threat-informed methodologies (e.g., adversary tactics or attack patterns) into risk assessment or control implementation expectations. This may limit the effectiveness of controls against evolving threats.
Recommendation: Integrate threat-informed guidance (e.g., mapping to adversary behaviors or attack frameworks) into RA and SI controls to ensure risk assessments and mitigations are grounded in real-world threat activity.

Gap #2 – Limited guidance on supply chain visibility and assurance depth
Issue: Updates to SR controls do not clearly define the expected depth of supply chain visibility (e.g., third-party vs. fourth-party dependencies), leading to inconsistent interpretations of responsibility.
Recommendation: Establish tiered expectations for supply chain risk management, including minimum requirements for visibility, monitoring, and assurance across different dependency levels.

Gap #3 – Lack of clarity on secure-by-design expectations in acquisition (SA)
Issue: The SA control updates emphasize security requirements but do not explicitly promote secure-by-design or secure-by-default principles during system acquisition and development.
Recommendation: Incorporate language requiring secure design principles (e.g., least privilege, default deny, resilience) to be embedded early in acquisition and development lifecycles.

Gap #4 – Ambiguity in boundary definition for system communications (SC)
Issue: The RFC does not sufficiently clarify how system boundaries should be defined in modern architectures (e.g., microservices, APIs, service meshes), which impacts the application of SC controls.
Recommendation: Provide updated boundary definition guidance and examples for cloud-native architectures to ensure consistent application of communications protection controls.

Gap #5 – Insufficient emphasis on data-centric security controls
Issue: The updates focus heavily on system and network protections but provide limited emphasis on protecting data itself (e.g., data classification, tagging, and flow tracking).
Recommendation: Expand SC and SI guidance to include data-centric security practices, ensuring protection persists regardless of infrastructure or location.

Gap #6 – Limited operational guidance for vulnerability and remediation timelines
Issue: SI control updates do not clearly define expectations for vulnerability remediation timelines or prioritization, which may lead to inconsistent risk responses across CSPs.
Recommendation: Introduce risk-based remediation timelines (e.g., tied to severity or exploitability) and require documented prioritization strategies.

Gap #7 – Lack of integration with DevSecOps pipelines
Issue: The RFC does not explicitly address how updated controls (especially SA and SI) should be implemented within automated CI/CD and DevSecOps pipelines.
Recommendation: Provide guidance on integrating security controls into development pipelines, including automated testing, code scanning, and deployment gating.

Gap #8 – Minimal consideration for cross-control data flows and dependencies
Issue: Controls across RA, SC, and SI rely on shared data (e.g., logs, telemetry, risk inputs), but the RFC does not address how these data flows should be standardized or integrated.
Recommendation: Define expectations for interoperability and data sharing between control implementations to enable cohesive security operations and analytics.

Gap #9 – No explicit expectations for validation of third-party security claims
Issue: While SR and SA controls emphasize supplier requirements, there is limited guidance on how CSPs should validate vendor security claims or attestations.
Recommendation: Include requirements or best practices for independent validation (e.g., third-party assessments, attestations, or continuous monitoring of vendors).
