# VDR/VER Migration Reporting Q&A / General Discussion

On Tue Nov 10, 2026, FedRAMP released [Public Notice NTC-0017 VDR/VER Migration Progress Reporting and Upcoming FY27 Q1 FedRAMP Security Inbox Test](https://www.fedramp.gov/notices/0017/). 

This Notice explained that FedRAMP will be collecting Progress Reports from all FedRAMP Certified cloud service providers who are expected to migrate to the VDR/VER rules and explained how that information will be collected.

It included the [VDR/VER Migration Resources](https://www.fedramp.gov/vdr-migration/) website for additional information on Progress Report collection, including deadlines, corrective action plans, schemas, and more.

---

Collecting progress reports from nearly 600 cloud services is obviously a massive undertaking. We weren't even sure if it was feasible, to be honest. This is partially a test to see how it goes. In the future when folks have adopted CR26 or future consolidated rules things will be much easier as we can simply programmatically monitor everyone's information but today we still need to ask for progress reports.

**This thread is dedicated to questions or feedback about this process, including the content, instructions, schemas, etc.**

There’s no way to file a Progress Report or CAP before the Emergency Test arrives. Providers should prepare and test early, but filing happens through the test. A VDR/VER CAP sent to FedRAMP some other way before then still has to go in through the Emergency Test.

Right now, the migration guidance has a couple of nuances we want to be sure we interpret correctly:

1. **MUST / MUST NOT rules (`Partially Implemented` or `Not Implemented`):**
   - Our reading is that every applicable `MUST`/`MUST NOT` rule is expected to be `Fully Implemented` by December 7, and any `Partially Implemented` or `Not Implemented` `MUST`/`MUST NOT` rule **must** include `customerRisk`, `providerCompensation`, `agencyCompensation`, and an active CAP (`Planned`, `In Progress`, or `Pending Plan`)—with `capStatus: Not Applicable` never permitted to waive an incomplete `MUST`/`MUST NOT` rule. Is that exact?

2. **SHOULD / SHOULD NOT rules (`Fully Implemented` vs. `Partially Implemented` vs. `Not Implemented`):**
   - `index.md` defines *"fully migrated"* as: all `MUST`/`MUST NOT` rules fully implemented, and all `SHOULD`/`SHOULD NOT` rules *"fully implemented **OR otherwise addressed**."*
   - `reference.md` notes that incomplete `SHOULD`/`SHOULD NOT` rules need an explanation, resulting risk, and compensation options, while `schemas.md` states that *"a justified SHOULD departure ... can also use CAP status `Not Applicable`"* (as shown in the `harbor.json` example for `VER-EVA-GRV`).
   - Could you clarify:
     1. Is `Partially Implemented` or `Not Implemented` on a `SHOULD`/`SHOULD NOT` rule—paired with `explanation`, `customerRisk`, `providerCompensation`, `agencyCompensation`, and `capStatus: Not Applicable`—considered *"otherwise addressed"* (and therefore **"fully migrated"** without needing a remediation target date or risking *"In Remediation"* status in February)?
     2. Or are there specific `SHOULD` rules / scenarios where FedRAMP expects a `Planned`/`In Progress` CAP rather than a documented departure (`capStatus: Not Applicable`), and what makes a `SHOULD` departure sufficiently justified during February review?
