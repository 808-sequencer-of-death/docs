# Five rules have two requirement levels but one force value
Source: https://github.com/FedRAMP/community/discussions/193

## Original post — kevinraymond, 2026-11-06T17:52:55Z

Five rules in 2026.11.02.01 use two requirement keywords in one statement, and `force` in `fedramp-consolidated-rules.json` can only have one.

| Rule | `force` | The statement also says |
|---|---|---|
| CDS-CSO-RIS | MUST | "... but SHOULD NOT include sensitive information ..." |
| CDS-TRC-ACL | MUST | "... SHOULD be made available upon request by those parties." |
| MAS-CSO-SUP | MAY | "... MUST be clearly marked and separated from the cloud service offering." |
| SCN-CSO-EMG | MAY | "In such emergencies, providers MUST follow all relevant procedures ..." |
| VER-RPT-NID | MUST NOT | "... but MUST disclose sufficient information ..." |

Anything that reads `force` to build a requirement list gets half of each rule. For example, filtering on MUST misses the MUST in MAS-CSO-SUP and SCN-CSO-EMG, because those are filed under MAY.

The new rule proposed in FedRAMP/rules#52 (IEC-CSO-RID) looks the same "MUST NOT ... but MUST" pattern as VER-RPT-NID, so that would be another.

I'm not sure what the correct way to handle it should be, but I can think of a few options:

1. Split each of these into two rules, one per requirement level.
2. Keep one rule and let `force` have more than one value.
3. Add a note to AGENTS.md that `force` is the primary level but the statement can carry a second one (doesn't touch the data).

I'm mentioning this because #190 asks for a flat list of rule IDs with the force for each, and that list would miss the second keyword for these rules.

Thanks for your great work!

## pete-gov (FedRAMP) — [2026-11-06T18:20:30Z](https://github.com/FedRAMP/community/discussions/193#discussioncomment-19446546)

These edge cases in particular have always been a bit of a complicated thorn - they are specific situations where we felt that having the secondary requirement directly inside the rule was critical because it applied _specifically to the rule_ in a way that it needed to be directly in there to avoid confusion.

The trick is that they're secondary, contingent on the first part, so the core force of the rule is still the main thing that matters for determining the approach to implementation.

- [CDS-CSO-RIS (Responsible Information Sharing)](https://www.fedramp.gov/2026/reference/certification-data-sharing/#responsible-information-sharing) - In short, Providers MUST supply information but SHOULD NOT include dangerous stuff when they do. We have separate rules about responsible sharing etc. in other rulesets but wanted to be very explicit in this top level rule because historically people include dangerous stuff. Separating this out risks a situation where someone feels like they need to folow the "MUST supply information" but can ignore the "SHOULD NOT include dangerous stuff."

- [CDS-TRC-ACL (Access Logging)](https://www.fedramp.gov/2026/reference/certification-data-sharing/#access-logging) - we could probably have separated these out without too much confusion, but having a random rule sitting around saying "access information should be made available upon request to parties that it pertains to" is a little scary. 

- [MAS-CSO-SUP (Supplemental Information)](https://www.fedramp.gov/2026/reference/minimum-assessment-scope/#supplemental-information) the MUST part is entirely irrelevant unless you've done the MAY part, creating an extra rule out of this would get weird.

- [SCN-CSO-EMG (Emergency Changes)](https://www.fedramp.gov/2026/reference/significant-change-notification/#emergency-changes) another situation there the MUST part is entirely irrelevant if the MAY part is done.

- [VER-RPT-NID (Responsible Disclosure)](https://www.fedramp.gov/2026/reference/vulnerability-evaluation-and-reporting/#responsible-disclosure) - these are so explicitly in tension that having them be separate rules would create a blocking loop for many compliance folks, but putting them together provides a structured approach. 

So I think the right approach for CR26 maintenance is your third suggestion "Add a note to AGENTS.md that force is the primary level but the statement can carry a second one (doesn't touch the data)." And to explain this in [Using the FedRAMP Consolidated Rules](https://www.fedramp.gov/2026/rules/).

Created [FedRAMP/rules#54](https://github.com/FedRAMP/rules/issues/54) to track this, thank you!
