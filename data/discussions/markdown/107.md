# Proposal for v1.0 of FedRAMP Machine-Readable Docs (w/ significant changes)
Source: https://github.com/FedRAMP/community/discussions/107

## Original post — pete-gov (FedRAMP), 2026-01-04T20:50:53Z

# Bottom Line Up Front

We are going to make some significant changes to the layout and labeling within FedRAMP's Machine-Readable Docs, including renaming of all requirement ID's, as part of the final push to a `v1.0` release of these materials.

This will be a breaking change that will require new parsers with different logic but will benefit from many lessons learned to create a more effective long term foundation for machine-readable requirements and recommendations.

# Background

[FedRAMP Machine-Readable Docs](https://github.com/FedRAMP/docs) have been in alpha since June, 2025. We've gone through a few massive evolutionary shifts of the machine-readable structure for these materials as well as the underlying approach to defining requirements and recommendations overall in the six months since.

I initially planned a bit of a retro and realignment to happen at the end of FedRAMP 20x Phase 2 but since then we have pushed heavily into Balance Improvement Releases for Rev5 that are starting to see wider adoption and shortly plan to initiate formal Wide Release for these materials in Rev5 - that means we need to get them into a somewhat fixed reliable state and initiate a formal `v1.0` release this month.

# Problems and Evolution

Our updated requirements in 2025 began with understanding that we needed to move away from long narrative descriptions into specific standalone statements. We refined these with technical assistance, definitions, exceptions, etc.

All of our requirements and rules were crafted in Google Docs, collaboratively edited, published for public comment, collaboratively edited again, then finally transferred into a JSON structure for future maintenance. The result is that the machine structure is **entirely** biased for capturing and recreating a specific **human-centric** way of thinking.

> A specific example of this is the Minimum Assessment Scope:
>
> 1. [RFC-0004](https://www.fedramp.gov/rfcs/0004/) uses a structured requirements format but has a lot of narrative text.
> 2. [RFC-0005](https://www.fedramp.gov/rfcs/0005/) creates formal definitions for the first time and creates more explicit, direct statements.
> 3. [The 25.06A human-readable release of the MAS](https://github.com/FedRAMP/docs/blob/a483755584843b7f701256fbf8d05e2378d91654/pdf/FRMR.MAS.minimum-assessment-standard.pdf) is the first labeled and explicitly structured set of requirements and recommendations machine-generated from JSON
> 4. [The 25.11C human-readable release of the MAS](https://www.fedramp.gov/docs/20x/minimum-assessment-scope/) is web-native, visually formatted, and includes additional metadata while being entirely machine-generated from JSON
>
> Notice how even the final version separates the document into numbered rules with labeled structures such as "Application" and "Exceptions"

As we've evolved these rulesets this has created more and more problems:

**The ID schema results in a perceived ordering that makes no sense and that leaves gaps and confusion.**

"Why does KSI-TPR start at 03 instead of 01?" or "Why do some rules have MUST requirements grouped together followed by SHOULD recommendations while they are interspered randomly in others?"

This is because everything was ordered for humans to read in a human way originally, resulting in all sorts of problems maintaining the materials. 

Also, stuff like "1.2.1.8.7" is annoying AF in general because it's based on everything around it - meaning if you delete some stuff all of a sudden it might become "1.1.1.7.2" then how are you going to handle it?

**Readability is inconsistent and labels are weird.**

Things like "FRR-PVA-TF-LO-02" make sense as a human structure (it's the second requirement that applies to low impact systems related to timeframes in the persistent validation and assessment standard) but creates semantic limits. 

> The PVA is a good example of an initial attempt to resolve this in spite of having terrible timeframe stuff - compare the various labeled subsections from [RFC-0017](https://www.fedramp.gov/rfcs/0017/) to the much fewer labeled subsections in the [25.11C release](https://www.fedramp.gov/docs/20x/persistent-validation-and-assessment/)

**Extending or modifying one set of rules means going back and rebuilding everything else. Having 10-15+ different JSON docs is to maintain is a pain.**

I knew this would happen but didn't expect it to happen so fast. I recently did a metadata reset for all of the docs and it was just bonkers.

Or, in some upcoming RFCs we are going to add "Corrective Actions" directly to some rules... which means we need to go back and add them to all rules. And they need to be different for 20x vs Rev5. One of the most effective ways to handle this is going to be embedded defaults across all sets of requirements so we're not jumping into a bunch of files to edit them.

**The whole FRR vs FRD vs FRA thing wasn't the best idea.**

Look, it made sense to me at the time to have separate things for all of this. 🤣  It still makes sense to manage definitions separately, but FRA stuff should be embedded directly in a requirement or recommendation.

**Sometimes all this ID stuff doesn't make sense.**

My favorite example of this is in the [human-readable version of the FedRAMP Definitions](https://www.fedramp.gov/docs/20x/fedramp-definitions/) - the ID's for each definition are _irrelevant._ No human will ever care about them when reading this documentation. It made no sense to order the human-readable documentation around it, but we did for six months because that was consistent with everything else.

**Lots of folks want both short labels and word-based summaries.**

We used an LLM to generate a bunch of summarized word-based summaries for each requirement or recommendation (that's how you get stuff like "FRR-ADS-08 Trust Center Migration Notification" and the response has been really positive, folks that have worked with these requirements generally really appreciate them and are often using one or both. They are really inconsistent though and it's not clear how they align with numbers.

**Calling out definitions gets a bit wonky.**

Originally we used italics to note that something is a definition but that's not really clear and it's all done manually, so sometimes its inconsistent. We shouldn't be using hard coded formatting within machine-readable requirements.

## Summary

We've done a good job of creating blunt, specific, easy to apply statements that make it clear who is responsible... and we've done a good job of structuring the JSON data built around that to make it practically a 1:1 representation of the human-readable source. 

It's turned into a pain to maintain and is unlikely to meet our needs going forward.

# Changes for `v1.0`

To address a lot of these lessons learned we're going to make a bunch of changes that will affect the underlying structure of the machine-readable requirements and recommendations files and the way they are displayed in human-readable versions; **but no actual requirements or recommendations will be materially changed.**

### 1. Everything will be combined into three JSON datafiles - KSIs, definitions, and others others.

KSIs will get their own JSON file because it's a whole thing and they have a wildly different structure in many cases - and that will probably expand a lot more. Same for Definitions.

Otherwise all of the other requirements and recommendations and definitions will be folded into a single file for combined maintenance because they should all consistently follow the same structure and be part of the same whole.

- Updates to each specific requirement or recommendation will tracked individually
- Only combined releases of the entire document set will be given formal versions
- Many other aspects of each specific requirement or recommendation will be tracked individually, such as applicability (including 20x vs Rev5), corrective actions, etc. as appropriate

### 2. Each requirement and recommendation will use a unique 3 stage identifier comprised of 3 letters each

No more than 3 stages will ever be used and nothing will start with FRR/FRD/FRA/etc.

- The first stage will use the existing process initialism such as `KSI`, `VDR`, etc.
- The second stage will use an initialism for a specific theme or subset of the process; this will vary by process. You're familiar with this for Key Security Indicators, such as `KSI-CNA` or `KSI-IAM` and it will be applied to other processes like changing `FRR-ADS-TC` to `ADS-TRC`. In general there will be some recurring themes, such as `ABC-GEN` to refer to general requirements.
- The third stage will use a unique initialism _that matches the human-readable short name_ instead of a number. For example, `KSI-AFR-07 Recommended Secure Configuration` will become `KSI-AFR-RSC Recommended Secure Configuration` or `FRR-MAS-04 Metadata Inclusion` might become `MAS-GEN-MDI`.
  - If 3 words really don't make sense then we'll use 3 letters that do or an X, for example `Independent Assessment` might become `IAS` or `Feedback Mechanism` might become `FMX` (or something like that)  

### 3. No more built-in human-readable formatting.

This mostly means removing italics - we'll address highlighting defined terms programmatically.

### 4. Simplify maintenance with JSON5

I'm going to experiment with using [JSON5](https://json5.org/) to make the underlying JSON file easier to maintain. This lets us add comments, quote things in different ways, not worry about trailing commas, carry text across newlines, etc. We'll make a final determination on this before we go live.

### 5. Fix earlier processes that have Application or other similar sections that aren't requirements or recommendations.

These will get integrated as either notes, technical assistance, or rephrased into something that makes more sense in context.

### 6. Maintain some backward compatibility.

We'll keep the old id's referenced where applicable to help people change over.

# Overall

This will create a pretty big change but it will let us consistently do more cool stuff, like:

1. Not worrying about "ordering" anything when we write new requirements and recommendations
2. Easily generate separate materials for things like providers, assessors, impact level, etc. without human-readable "gaps" appearing in materials
3. Separate the maintenance of terms in requirements to something that is entirely programmatic
4. Simplify referring to specific requirements or recommendations because they'll make sense ("MAS-GEN-SOF" is obviously separate from "MAS-GEN-SFT" and easier to context align than "FRR-MAS-AY-01" and "FRR-MAS-AY-02")

## Feedback/etc.

Any thoughts, feedback, etc. from folks that have been working with these materials in their JSON form would be appreciated. 

I recognize this is a large shift but it's one we need to do **before** the current requirements and recommendations are formally standardized into a non-pilot/beta state.

As I'm working a bit on porting this and updating, I'm also adding the following:

### timeframes and stuff

I'm going to add a couple metadata fields for timeframe related stuff:

- `timeframe_type` days / months / years
- `timeframe_num` is the number

This won't work for some of the fancier timeframes like "end of the week three weeks later" but is a start. This will also vary by level. 😭 

### varies_by_level

In situations where the same requirement or recommendation applies to different validation levels duplicative objectives with different impact statements, they will be combined into the same requirement and noted in a `varies_by_level` object.
