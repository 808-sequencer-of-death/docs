# FedRAMP Rev5 Security Controls Baseline Update for CP, IA, IR, MA, and MP Control Families

---

## **Summary**

This is a technical RFC that proposes updates to the Additional FedRAMP Security Technical Controls Requirements and Guidance for FedRAMP Rev5 baselines.

To save space and to limit the breadth of a single RFC, this technical document shows only the proposed changes to the current baseline document and is restricted to a few control families. If verbiage is being updated, only the specific wording that is to be changed is identified in the old verbiage section. If the verbiage to be added is not replacing previous verbiage, but being added, it will be identified as “NEW” in the old verbiage section.  

Since this spreadsheet covers hundreds of controls across multiple tabs and sections, only those specific controls, sections, and tabs identified are being proposed for updates. If it is not mentioned below, changes are **not** being proposed.  

**Commenters are advised to please mention specific controls in their comments!**

This RFC addresses controls in the following families:

* Contingency Planning (CP)  
* Identification and Authentication (IA)  
* Incident Response (IR)  
* Maintenance (MA)  
* Media Protection (MP)

## **Motivation**

Many Rev5 FedRAMP Requirements and Guidance statements are based on outdated approaches that predated the release of the FedRAMP Authorization Act and M-24-15. This set of Requirements and Guidance needs a refresh to match FedRAMP’s current rules and approach.

The updates formalized after this RFC will be included in the FedRAMP Consolidated Rules for 2026. That set of rules will be valid until December 31, 2028. FedRAMP will provide a transition plan for adopting any new guidance that will enable cloud service providers to update their approach as part of their annual assessment as appropriate.

These changes are designed to lower the burden for cloud service providers and eliminate previous pain points.

Additionally, NIST released 800-53 Rev 5.2.0 in August of 2025.  While this update was minor, control updates from NIST will require updates to FedRAMP Security Control Baseline in order to reflect this update.  These changes will happen without public comment through FedRAMP since these are direct reflections of NIST changes.  As subsequent iterations of the FedRAMP Security Control Baseline are published, it is FedRAMP’s intent only to carry over the following information from NIST 800-53; Control Family, Control Name, and Control ID. Following this will be FedRAMP-Defined Assignment / Selection Parameters and additional FedRAMP Requirements and Guidance.

Given the hyperactive threat environment around credential theft, the commoditization of e.g. phishing kits, and the ease with which people can be socially engineered, I think we need to start treating phishing-resistant MFA like we treat encryption protocols: be explicit about which kinds of MFA protocols/standards/patterns qualify as phishing-resistant, instead of specifying which kinds are **not** phishing resistant. FIDO2-based implementations of authentication credentials are really the only well known, well understood, easily accessible, and well vetted protocols/schemes for phishing-resistant authenticators (PIV/CAC PKI-based credentials can be considered phishing resistant but are really only common within government organizations). 

Let's be more explicit here about what is considered phishing-resistant to avoid instances of organizations "rolling their own" or rolling a vendor's purported "phishing-resistant MFA" product that uses proprietary protocols or implementation patterns that make it prone to remote credential theft. It would also make sense to explicitly define existing forms of hardware-backed authentication credential devices, such as PIV/CAC cards, as qualifying as phishing-resistant MFA.

Here's an example of what I mean (bolded text is my recommendation):

> IA-2 Requirement: For all control enhancements that specify multifactor authentication, the implementation must adhere to the Digital Identity Guidelines specified in NIST Special Publication 800-63B.
Multi-factor authentication must be phishing-resistant. Per CISA, One-time password (OTP), Mobile push notification with number matching and Token-based OTP are NOT phishing resistant. **Likewise, FIDO2-based authenticators and PKI-based authenticators, wherein a hardware-bound cryptographically-generated credential is used, are considered phishing resistant**
https://www.cisa.gov/sites/default/files/publications/fact-sheet-implementing-phishing-resistant-mfa-508c.pdf

Gap #1 – Limited guidance on shared responsibility in cloud-native environments
Issue: The RFC does not sufficiently clarify how updated controls (especially in IA, IR, and CP families) should be applied in shared responsibility models across IaaS, PaaS, and SaaS. This creates ambiguity in control ownership and assessment boundaries.
Recommendation: Include a mapping or explanatory guidance that distinguishes CSP versus customer responsibilities for each affected control family across different service models.

Gap #2 – Insufficient integration with automation and continuous monitoring
Issue: While controls are updated, there is minimal emphasis on how requirements should be implemented using automated or continuous monitoring approaches, which are central to modern FedRAMP practices.
Recommendation: Incorporate expectations or examples for automation (e.g., machine-readable evidence, APIs, continuous diagnostics) to align control implementation with ongoing authorization and real-time monitoring goals.

Gap #3 – Ambiguity in evidence expectations for assessments
Issue: The RFC updates control language but does not clarify what constitutes sufficient or acceptable evidence for assessors, increasing the risk of inconsistent 3PAO interpretations.
Recommendation: Provide supplemental assessment guidance or example evidence artifacts for updated controls to improve consistency across assessments and reduce rework.

Gap #4 – Transition guidance for existing authorizations
Issue: There is no clear direction on how currently authorized systems should transition to the updated requirements, including timelines, reauthorization triggers, or delta assessment expectations.
Recommendation: Define a transition strategy outlining applicability to existing ATOs, expected timelines, and whether updates can be incorporated through continuous monitoring or require formal reassessment.

Gap #5 – Interdependencies across control families not addressed
Issue: Updates to CP, IA, IR, MA, and MP controls may have operational dependencies (e.g., incident response tied to identity systems), but these relationships are not explicitly addressed.
Recommendation: Highlight key interdependencies and provide cross-references or implementation considerations to ensure cohesive and effective control implementation.

Gap #6 – Limited consideration for operational scalability
Issue: Some updated expectations may be difficult to operationalize at scale (e.g., in large, distributed, or multi-tenant environments) without additional clarification.
Recommendation: Include scalability considerations or implementation patterns for large CSP environments to ensure requirements remain practical and achievable.

## acloudcj — [2026-04-18T00:59:05Z](https://github.com/FedRAMP/community/discussions/132#discussioncomment-16608923)

IA (Identification and Authentication), Phishing Resistant MFA:
This is the most consequential change in the batch. Explicitly stating that OTP, mobile push with number matching, and token based OTP are not phishing resistant provides clarity that the field has needed. CSPs have been interpreting “phishing resistant” differently for years, and this draws a clear line.
The operational concern is timeline. Many CSPs, particularly those serving agencies that haven’t adopted FIDO2/WebAuthn, are running authentication stacks built on exactly the methods this RFC now excludes. The RFC doesn’t specify a transition period for IA controls specifically. Will CSPs currently using number matching push (which many adopted because it was considered an upgrade from basic push) have until their next annual assessment to migrate? Or is this effective on publication? The answer determines whether this is an orderly transition or a fire drill.
Also: the requirement to document authentication factors in SSPs and Architecture Boundary Diagrams is good practice, but the Architecture Boundary Diagram is already one of the most labor intensive artifacts in a FedRAMP package. Adding per factor documentation for every authentication flow, including those inherited from IaaS/PaaS providers, could significantly expand the diagram. Is the expectation that CSPs document their own authentication factors only, or also the factors implemented by underlying service providers within the authorization boundary?
IR-06 (Incident Reporting), FedRAMP Secure Inbox:
Adding the FSI as the centralized point of contact for incident reporting and VDR related communications is a sensible consolidation. The question is about response rate expectations. The RFC references “appropriate response rates” per FSI Guidance, but from the CSP side, the FSI has historically been unidirectional. CSPs submit; responses come when they come. If FedRAMP is now establishing response rate expectations for CSPs, reciprocal SLAs for FedRAMP acknowledgment and triage would build confidence that the inbox is actively monitored and not a queue that grows faster than it drains.
MA (Maintenance), Nationality Documentation:
This mirrors the same requirement in RFC-0029 for personnel security. The policy question is the same in both places: what does “where applicable” mean? Some CSPs operate globally and use maintenance contractors across multiple countries. Others are US only. “Where applicable” without criteria leaves CSPs guessing whether they need to document nationality for every contractor or only when a specific condition triggers. Even a short list of conditions (clearance requirements, physical access to federal data, access to FedRAMP boundary systems) would make this actionable.
CP-2(8), Essential Parameter:
Adding “[essential]” as the parameter value for CP-2(8) is fine, but this same parameter reference appears in CM-12(1) in RFC-0027 without explanation. These should be cross referenced so reviewers understand the relationship between contingency planning essentiality designations and information location tracking.

Support for this set of changes. Several items deserve specific comment.

Please find below my public comments on RFC-0028 FedRAMP Rev5 Security Controls Baseline Update for CP, IA, IR, MA, and MP Control Families.

**Comment 1 :** IA-02, IA-02(1), IA-02(2) 

Clarifying that OTP, mobile push with number matching, and token-based OTP are not considered phishing-resistant moves the documentation in the right direction. This has come up many times during 3PAO assessments in the past — there's a legitimate belief on behalf of CSPs that number-matched push is in scope. Referencing the CISA fact sheet directly as normative is appropriate.

That being said, why does the proposed control language fail to make a distinction between FIDO/WebAuthn and PKI-based MFA? The entire reason behind the CISA fact sheet exists because PKI/PIV deployments require preexisting identity infrastructure most commercial CSPs aren't going to have. Grouping both technologies together as if they're equally viable options for this requirement is going to lead to questions/shortfalls during SSP creation.

**Comment 2 :**  CP-02

Updating the old ISCP template link to the active version is simple and very helpful. Assessors and CSPs alike have been coping with this broken link for too long.

However, there is one process-improvement opportunity to point out. The default ISCP template (Appendix G) includes version and approval date fields that are almost universally left blank between annual updates. This creates unnecessary findings during assessment even when the plan itself is up-to-date and comprehensive. Linking ISCP versioning requirements to CP-03 review lifecycle would solve this issue with no need to redesign the template.

**Comment 3 :**  IR-07 and MA-05

Both controls make sense as additions. Mandating CSPs to retain a point of contact for FedRAMP Secure Inbox (IR-07) is well past due, as this is a gap we see frequently in smaller organizations who may not have a formal security staff. And requiring nationality proof/documentation for MA-05 subcontractors is certainly headed in the right direction with the federal SCRM strategy moving forward.

Something that jumped out as inconsistent between the two — IR-07 uses "must" language while MA-05 only uses "should." If the intent is to have these controls enforced for all customers regardless of baseline, this difference will almost certainly lead to confusion from assessors in the field.
