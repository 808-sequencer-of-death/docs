## BPFanelli — [2025-08-12T18:57:08Z](https://github.com/FedRAMP/community/discussions/72#discussioncomment-14085600)

A bastion was the easy button. For any other configuration, the access point needed to:
- Be inside an authorized boundary - not necessarily the instant CSO's boundary (see below)
- Audit all access traffic
- Meet the appropriate AAL requirements to authenticate users

When accessing a CSO boundary from another CSO, the access should be network adjacent, for example:
- Access from AWS Workspace into an AWS VPC is acceptable
- Access from Google Workspace into an AWS VPC is questionable

Questionable means it did not happen very often, and there was no defined rule established. In general, the question was - If the connection is going to be made over the Internet (rather than remaining within a single CSO's authorized environment):
- Can it be considered as having met the SC-7b requirement, or
- Does it need to meet SC-7b within the boundary
If the former, at a minimum, there needs to be very tight controls on the connection over the Internet to prevent spoofing

I suggest any new guidance take these points into account. After I take input here, I will move my final comments to the comment page.

## BPFanelli — [2025-08-12T19:29:26Z](https://github.com/FedRAMP/community/discussions/72#discussioncomment-14085832)

Here is the guidance that was distributed for Agency packages when it came up. It is derived from the guidance in **BOD 23-02 Implementation Guidance** _Figure 4 - Acceptable use case – networked management interfaces only accessible from management network micro-segments through zero trust policy enforcement point (ZT PEP)_.
https://www.cisa.gov/news-events/directives/binding-operational-directive-23-02-implementation-guidance#:~:text=Figure%204%20%2D%20Acceptable%20use%20case%20%E2%80%93%20networked%20management%20interfaces%20only%20accessible%20from%20management%20network%20micro%2Dsegments%20through%20ZT%20PEP.

Summary of CISA zero trust (ZT) policy enforcement point (PEP) guidance:
- Implements authentication and authorization separate from any interface being accessed
- Must be inside an authorized boundary
- Configuration console and gateway must both be in an authorized boundary
- Traffic from administrators to the ZT PEP is mutually authenticated
- Traffic from the ZT PEP to any internal interface is mutually authenticated and authorized, where possible

## BPFanelli — [2025-08-27T18:11:33Z](https://github.com/FedRAMP/community/discussions/72#discussioncomment-14236212)

Here is another topic for conversation. 

I would like to open with the seemingly controversial position that SC-7b actually does provide security benefits. In SC-7b's defense, my recent correspondence with the SP 800-53 authors reminds me that all controls, particularly SC-7b, must be evaluated in the context of the surrounding control parts and enhancements. Given this context, I would like to turn to the technical side of why subnets are such a hot topic - and what to do about that.

Again, to the extent that SC-7b provides security benefits, it presumes that the subnets follow normal TCP/IP rules. That last part is important because the software defined networks (SDNs) in many hyperscales deviate at layer 2 and layer 3 in both behavior and configuration. In addition, no two hyperscales tweak the TCP/IP rules in the same way.

For example:
- One CSO assigns every VM a /32 mask (aka 255.255.255.255) as if it were the only host in a subnet
- Another allows subnets to span VPCs, where another does not

The most likely alternative implementation falls to security groups (SGs). Similarly SGs are/may be implemented differently in each hyperscale environment. For example:
- One CSO clearly applies SG access rules at the interface level regardless of where the rule set is assigned
      - That is, SG rules assigned to a VPC will flow down and actually be implemented and enforced on each interface in the VPC
- Other CSOs may do the same, but it is not as clear in their documentation

**Takeaways from the above:**
- SC-7b presumes that subnets are following TCP/IP rules as defined by IETF
- SDN environments deviate from standard layer 2 and layer 3 in both behavior and configuration
- No two CSPs appear to implement their TCP/IP tweaks in the same way
- Similarly CSPs may implement SGs in different ways

**Conclusions I draw from these takeaways:**
- SDNs and SGs as implemented by hyperscales offer great alternatives to subnetting
- Given that each CSP has their own flavor, it is difficult to impossible to specify a general rule for an exception
- It then falls to each IaaS/PaaS that implements SDN tweaks to:
      - Define the inheritable capability in their environment as an alternative implementation
      - Engage with their 3PAO to get this assessed
      - Document this in their CRM

Thoughts?
