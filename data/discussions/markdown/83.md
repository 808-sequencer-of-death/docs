## Summary & Motivation

FedRAMPs Key Security Indicators summarize the security capabilities expected of a cloud service provider who wishes to obtain and maintain a FedRAMP 20x authorization. These capabilities are broadly summarized with the expectation of broad automated application.

This RFC summarizes proposed changes to the existing Key Security Indicators where they were ineffective, unclear, or insufficient. This RFC also proposes new Key Security Indicators for both FedRAMP Low and FedRAMP Moderate to resolve outstanding gaps and integrate additional controls.

Keen observers will note that there are very few new Key Security Indicators required for Moderate; this is because almost every single Moderate control is already covered by an existing or slightly modified Key Security Indicator. Cloud service providers seeking Moderate authorization during the Phase Two pilot will need to demonstrate _significantly_ approved maturity in both depth and automation related to all Key Security Indicators; simply adopting the new Key Security Indicators will not be sufficient.

During Phase One FedRAMP would accept written attestation that some Key Security Indicators were met for a Low authorization. During Phase Two, FedRAMP will expect truly automated and opinionated validation of Key Security Indicators for a Moderate authorization. For example, KSI-PIY-06 expects validation that a provider has staff and budget for security - FedRAMP accepted attestations about general budget or staffing numbers for Low but will expect to see automated validations demonstrating the participation and involvement of security staff in common operations to prove this validation is met for Moderate.

For this and other Key Security Indicators, FedRAMP plans to publish simple Technical Assistance prior to accepting submissions for Phase Two. In the interim, the FedRAMP Community [20x Pilot Review Feedback Friday](https://github.com/FedRAMP/community/discussions/69) discussion contains many pro-tips for navigating Key Security Indicators.

# **Retired Key Security Indicators & Validations**

The following Key Security Indicators & Validations have been retired because they were replaced by a separate set of requirements and recommendations included in a specific FedRAMP standard (these will live on as empty indicators during Phase Two).

### KSI-MLA-04:

* Previous: *Perform authenticated vulnerability scanning on information resources*  
* Updated: **Superseded by KSI-MLA-03**

### KSI-MLA-06:

* Previous: *Centrally track and prioritize the mitigation and/or remediation of identified vulnerabilities*  
* Updated: **Superseded by KSI-MLA-03**

### KSI-TPR-02:

* Previous: *Regularly confirm that services handling federal information or are likely to impact the confidentiality, integrity, or availability of federal information are FedRAMP authorized and securely configured*  
* Updated: **Superseded by KSI-TPR-01**

# **Updates to Key Security Indicators & Validations**

The following Key Security Indicators & Validations have been updated with different text to refine, clarify, or extend the requirement.

### KSI-CED-01:

* Previous: Ensure all employees receive security awareness training  
* Updated: Ensure all employees receive security **and privacy** awareness training**, incident response training, and are familiar with all relevant policies and procedures.**

### KSI-CMT-01:

* Previous: Log and monitor system modifications  
* Updated: Log and monitor **service** modifications

### KSI-CMT-03:

* Previous: Implement automated testing and validation of changes *prior to deployment*  
* Updated: Implement **persistent** automated testing and validation of changes

### KSI-CMT-04:

* Previous: *Have* a documented change management procedure  
* Updated: **Consistently follow** a documented change management procedure

### KSI-CNA-01:

* Previous: Configure ALL information resources to limit inbound and outbound traffic  
* Updated: Configure ALL **machine-based** information resources to limit inbound and outbound traffic

### KSI-CNA-05:

* Previous: *Have* denial of service *protection*  
* Updated: **Protect against** denial of service **attacks and unwanted spam**

### KSI-IAM-05:

* Previous: *Apply zero trust design principles*  
* Updated: **Design identity and access management systems that assume resources will be compromised**

### KSI-INR:

* Previous: Incident *Reporting*  
* Updated: Incident **Response**

### KSI-INR-01:

* Previous: *Report* incidents according to FedRAMP requirements and cloud service provider policies  
* Updated: **Respond to** incidents according to FedRAMP requirements and cloud service provider policies

### KSI-MLA-03:

* Previous: Rapidly detect and *remediate or mitigate vulnerabilities*  
* Updated: Rapidly detect and **respond to vulnerabilities following requirements and recommendations in the FedRAMP Vulnerability Response and Detection standard**

### KSI-PIY-01:

* Previous: *Have an up-to-date information resource inventory or code defining all deployed assets, software, and services*  
* Updated: **Generate inventories of information resources from authoritative sources**

### KSI-PIY-02:

* Previous: *Have policies outlining the* security objectives *of all information resources*  
* Updated: **Document the** security objectives **and requirements for each information resource**

### KSI-PIY-04:

* Previous: Build security considerations into the Software Development Lifecycle and align with CISA Secure By Design principles  
* Updated: Build security **and privacy** considerations into the Software Development Lifecycle and align with CISA Secure By Design principles

### KSI-PIY-06:

* Previous: Have *a dedicated staff* and budget for security *with executive support,* commensurate with the size, complexity, scope, and risk of the service offering  
* Updated: Have **staff and budget for security** commensurate with the size, complexity, scope, **executive priorities**, and risk of the service offering **that demonstrates commitment to delivering a secure service.**

### KSI-SVC-01:

* Previous: *Harden and review network and system configurations*  
* Updated: **Continuously evaluate machine-based information resources for opportunities to improve security**

### KSI-SVC-03:

* Previous: Encrypt *all federal and sensitive* information at rest  
* Updated: Encrypt information at rest **by default**

### KSI-SVC-04:

* Previous: Manage configuration *centrally*  
* Updated: Manage configuration **of machine-based information resources using automation**

### KSI-SVC-05:

* Previous: *Enforce system and information resource integrity through cryptographic means*  
* Updated: **Use cryptographic methods to validate the integrity of machine-based information resources**

### KSI-TPR-01:

* Previous: *Identify all third-party information resources*  
* Updated: **Follow the requirements and recommendations in the FedRAMP Minimum Assessment Standard regarding third-party information resources**

# **New Key Security Indicators & Validations**

## Low

The following Key Security Indicators & Validations have been created that affect the Low (and Moderate) baseline.

### KSI-CED-03:

* Require role-specific training for development and engineering staff covering best practices for delivering secure software.  
* Applies to: Low, Moderate

### KSI-IAM-07

* Securely manage the lifecycle and privileges of all accounts, roles, and groups.  
* Applies to: Low, Moderate

### KSI-MLA-07

* Maintain a list of information resources and event types that will be monitored, logged, and audited.  
* Applies to: Low, Moderate

## Moderate

The following Key Security Indicators & Validations have been created that affect the Moderate baseline:

### KSI-CNA-08

* Use automated services to persistently assess the security posture of all services and automatically enforce secure operations.  
* Applies to: Moderate

### KSI-MLA-08

* Use a least-privileged, role and attribute-based, and just-in-time access authorization model for access to log data.  
* Applies to: Moderate

### KSI-SVC-08

* Ensure that changes do not introduce or leave behind residual elements that could negatively affect confidentiality, integrity, or availability of information resources.  
* Applies to: Moderate

### KSI-SVC-09

* Use mechanisms that continuously validate the authenticity and integrity of communications between information resources.  
* Applies to: Moderate

### KSI-SVC-10

* Remove unwanted information promptly, including from backups if appropriate.  
* Applies to: Moderate

## jdettweiler — [2025-09-11T16:16:10Z](https://github.com/FedRAMP/community/discussions/83#discussioncomment-14376091)


There are some interesting updates in this RFC release, please consider the following feedback: 

**KSI-CED-01**: - Update was clearly made to include all required training based on the moderate baseline, why was contingency plan training excluded? Should it be included? I know most organizations combine IR/CP training into functional and tabletop exercises but was just curious if the exclusion was an oversight or purposeful. 

**KSI-CMT-01:** - Clearly the change from “system” to “service” was very purposeful, but to me “system” seemed to be all inclusive while “service” seems to scope the KSI requirements to a subset. Is there an explanation for this very purposeful word change? Would it be possible to add the definition of “service” and “system” to the [FRMR.FRD](https://github.com/FedRAMP/docs/blob/main/markdown/FRMR.FRD.fedramp-definitions.md) definitions? 

**KSI-CMT-03:** - The use of the word “persistent” [based on the definition](https://github.com/FedRAMP/docs/blob/main/markdown/FRMR.FRD.fedramp-definitions.md#frd-all-38): “Occurring in a firm, steady way that is repeated over a long period of time” and associating it with changes creates a slight dichotomy. For “routine recurring” changes, I can see this meaning that each time one of these changes is pushed, there should be a way to demonstrate it was tested prior to production and then post deployment (i.e., impacts to configuration/security baseline based on change). I assume this is why “prior to deployment” wording was removed indicating a desire to know impacts of change as part of deployment pipelines AND on production system state.

## rcfl33man — [2025-09-11T19:52:47Z](https://github.com/FedRAMP/community/discussions/83#discussioncomment-14377646)

The proposed KSIs for FedRAMP 20x Phase Two appear to omit explicit mapping to NIST SP 800-53 Rev 5 CA-8 and CA-8(2). While the shift toward automated, continuous validation represents a significant improvement over prior reliance on point-in-time attestations, the removal of adversarial testing requirements creates a material assurance gap.

**Rationale:**
- KSIs confirm that controls exist and are technically enforced, but they assume those controls are effective. Penetration testing and red teaming validate whether controls withstand a skilled adversary’s attempts to bypass or manipulate them, providing real-world assurance.
- Based on our engagements, many weaknesses or vulnerabilities are the result not from missing controls but from misconfiguration, weak operational processes, or human error. Red team exercises uniquely test people and organizational response which is something no automated KSI can replicate.
- FedRAMP 20x introduces stronger requirements for third-party resources. However, adversarial testing is often where supply chain and integration weaknesses are uncovered. Without it, CSPs may meet KSI requirements on paper but still expose agencies through poorly secured dependencies and boundary weaknesses.
- Automated KSIs largely validate against known control requirements. Adversarial testing exposes emergent vulnerabilities such as vulnerability chaining, misused privileges, or race conditions attack vectors that cannot be fully enumerated in advance.
- Federal systems are high-value targets for APTs. NIST retained CA-8 precisely because adversarial testing reflects APT tactics, techniques, and procedures. Excluding CA-8 risks under-preparing CSPs for nation-state-level adversaries.
- Other major security frameworks all maintain penetration testing or red team requirements. Removing CA-8 from FedRAMP 20x creates divergence from established best practice, potentially reducing confidence in CSP authorizations (not to mention Agency buy in).

**Recommendations**
FedRAMP should reinstate CA-8 requirements or introduce a new KSI explicitly mandating periodic adversarial testing. Suggested cadence:
- At least annually for Moderate baselines, with risk-based frequency for higher-impact systems.
- Integration of pen test/red team results into automated validation pipelines (vulnerability management, etc.), ensuring lessons learned feed back into continuous monitoring.

Automated KSIs are a positive step toward scalable, continuous assurance, however they may be less sufficient. Without penetration testing and red teaming, FedRAMP 20x risks creating blind spots, diverging from 800-53 intent, and underestimating modern threats. A hybrid model continuous KSIs plus incorporating periodic penetration testing/red teaming (based on risk profile) would deliver the most robust assurance for federal systems.

**Penetration Testing and Red Teaming:**  

None of the Moderate KSIs reference penetration testing or red teaming, which creates a critical gap. The current KSIs are weighted heavily toward infrastructure-layer security, with minimal focus on validating the application layer – where many of the most exploitable flaws actually exist. While it’s our interpretation that DAST/SAST scanning falls under the Vulnerability Response and Detection standard, vulnerability scanning alone cannot and should not replace penetration testing and red teaming. 

Penetration testing and red teaming remains the most effective way to identify real-world attack paths, uncover business logic flaws, and validate layered defenses. Without it, organizations risk overlooking high-impact vulnerabilities that automated scans are not designed to detect.  In 2024 alone, Schellman’s penetration testing team identified more than 1,000 vulnerabilities in FedRAMP-authorized cloud services ([source](https://www.schellman.com/blog/penetration-testing/penetration-testing-key-stats)). Under the current 20x Moderate model, those same 1,000+ vulnerabilities would not have been detected and left open to sophisticated attackers for exploitation. 

Relying solely on automated checks risks giving agencies a false sense of security.  While 20x’s automation efforts provide a great start, true security depends on skilled professionals who think like attackers, uncovering misconfigurations, human error, unsecured APIs, shadow IT, inadequate separations, and chained exploits that automation cannot detect.  

FedRAMP should double down on penetration testing and red teaming requirements by ensuring that: 
- 3PAOs performing tests are qualified with proven expertise, and 
- 3PAO methodologies emphasize real-world security testing rather than “check-the-box” compliance.

# RFC 0014 Comments

## KSI-CNA-01, KSI-SVC-01, KSI-SVC-04, KSI-SVC-05

The changes to the KSIs limit network policies to "machine-based" systems, offering a narrowed definition and excludes critical cloud-native resources. Modern infrastructure relies heavily on managed services *(databases, object stores, queues, Kubernetes APIs)* that must be subject to least privilege network policies. While most Cloud Service Providers have limited functionality for this, they often have the ability to restrict both user access and NHI access based on approved IP ranges. Limiting this to “machine-based” only, leaves out large swaths of modern infrastructures. 

**Recommendation:** Expand the requirement to: “Configure all machine-based (hardware and virtual), container based, orchestration, and cloud-based services to limit inbound and outbound traffic.”

**Benefit:** This change would broaden the scope to include modern infrastructure like managed databases, object stores (S3), queue services, Kubernetes APIs *(EKS, GKS, AKS)*, and serverless functions, ensuring they are also subject to least privilege network policies.

**Example:** 

* Managed Databases  
* Object Stores (S3, etc)  
* Queue Services  
* Kubernetes Management APIs (EKS, GKS, AKS, etc)  
* Serverless (Lambda, Functions, etc)

None of the above should be excluded from least privilege network policy. 

As an example, with KSI-CNA-01, this can be achieved with services like PrivateLink and/or Security Group restrictions on the cloud service itself. Each hyperscaler has a similar approach. 

## KSI-IAM-05

* Previous: *Apply zero trust design principles*  
* Updated: Design identity and access management systems that assume resources will be compromised

We respectfully disagree with the proposed change. ZeroTrust principles necessitate that policies operate under the assumption that all resources may be compromised. Beyond identity, the foundational pillars of ZeroTrust are network and device. Consequently, it is imperative that both network and device policies are integrated into the identity policy. For instance, CSPs should be required to demonstrate that their devices are both trusted and restricted. Furthermore, devices should have an associated network policy to ensure that a service or API remains inaccessible in the event of a credential compromise or replay attack. Associating network policies with every identity is paramount to preventing an exploit should credentials be compromised. 

**Recommendation:** Reword as: “Design identity and access management systems with comprehensive policies including ZeroTrust principles such as network and device policy restrictions”

**Benefit:**  A refinement to the current wording would enhance the clarity of the standard. This adjustment would explicitly incorporate critical Zero Trust pillars beyond identity, specifically network and device policies. This inclusion is considered essential until more robust standards, such as the OpenID Foundation’s Interoperability Profiling for Secure Identity in the Enterprise (IPSIE) and DPoP, achieve widespread adoption.

**Example:** As highlighted in the SalesLoft Drift incident, IP and device restrictions are essential until stronger standards *(e.g.. IPSIE, DPoP)* are widely adopted. 

[https://www.okta.com/newsroom/articles/the-salesloft-incident--a-wake-up-call-for-saas-security-and-ips/](https://www.okta.com/newsroom/articles/the-salesloft-incident--a-wake-up-call-for-saas-security-and-ips/)

From the article, there is a future here in terms of greater security in the form of IPSIE and DPoP. Until then, we should rely on IP/Network restrictions and device policy restrictions.

Love this. Thank you for this change. I often advise teams that they should be automating their changes. Having this control now gives me a reference for them to understand expectations. We need to move toward a more DevSecOps approach to “repeatable” deployments and change management. ClickOps has to be a thing of the past. 

## KSI-MLA-08

* Use a least-privileged, role and attribute-based, and just-in-time access authorization model for access to log data.  
* Applies to: Moderate

For KSI-MLA-08, we recommend clarifying whether all of the above apply or if it’s either/or. Just in time (JIT) access models are harder to implement and may not be appropriate in all cases. JIT may be useful for accessing specific data or services on an occasional basis as to maintain Zero Standing Privileges, but for operators who manage service on a regular basis, JIT access requests can become a burden for response, especially if they have to request access to services every time they need to look at something. Basically JIT access makes sense for requests that fall outside of someone’s typical role. Long story short, this could be a dissertation about where JIT access and Zero Standing Privileges make sense. For the purposes of this KSI, this should all be either/or.

Old roles, policies, ebs volumes (storage), unused services, etc. Without an automated change process (which removes the old stuff), residual elements will always get left behind. The main thing I would test for here is an automated change process which should include an automated de-provisioning process. This is easy to meet with Terraform, CloudFormation, etc.

Appreciate the ongoing engagement from @pete-gov and the FedRAMP team - wanted to share a quick perspective as a CSP not selling penetration testing services.

The FedRAMP 20x standard should not go backwards by imposing a separate, one-size-fits-all “red-team” mandate. Human-led penetration testing and red teaming are already embedded within the VDR requirement (KSI-MLA-03), which is designed for ongoing detection, not a fixed annual checkbox.

Instead, CSPs should focus on automation and continuous controls validation - automating vulnerability detection, misconfiguration checks, and attack-path simulations - so that human-led testing can be triggered when risk indicators justify it. This enables real-time detection of configuration drift and rapid response to emerging threats, while reducing the cost, scheduling overhead, and redundancy of fixed-schedule red-team exercises.

By contrast, a blanket red-team mandate can drive higher costs, rigid scheduling, and lower signal-to-noise when conducted annually without regard to actual risk.

Automation combined with risk-triggered human testing produces stronger assurance, aligns with 20x’s modernization goals, and ensures we’re investing resources where the real risk lies.

Hi FedRAMP team, getting my comments in here. Overall, exceptional work. I have a comment specifically regarding KSI-PIY-01. The current wording of "Generate inventories of information resources from authoritative sources" is too vague. Normally I am a fan of open-ended standards that aren't overly prescriptive, but in this case I'd recommend tweaking the language to explicitly recommend the use of Package URL (PURL) format where applicable in order to ward off potential automation-breaking problems. The update looks like this:

KSI-PIY-01: Generate inventories of information resources from authoritative sources. For software components, SHOULD use Package URL (PURL) format to enable precise identification, version tracking, and supply chain risk management.

The VDR standard creates a dependency chain on inventory: KSI-PIY-01 (inventory) → SBOM generation → PURL identifiers → VDR compliance (i.e., KSI-MLA-03). Making inventory identifiers open ended would unravel this automation chain, making it virtually impossible to align on meaningful "apples to apples" metrics for many of the KSIs.

Similarly, for the SCN standard there is a dependency chain on inventory as well: KSI-PIY-01 (Inventory with PURL) → Change Detection & Categorization → SCN Compliance (FRR-SCN-03) → Automated Machine-Readable Reporting (FRR-SCN-08). Without a means of precisely identifying versioned components, it is virtually impossible to adequately scope changes at scale and validate their security comprehensively in an automated manner, undermining the SCN standard's core premise of agile deployment without advance government approval.
