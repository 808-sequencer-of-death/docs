# Does FedRAMP consider quantum vulnerable cryptography a vulnerability?

Given the acceleration of Post Quantum Computers and the risks associated with harvest and decrypt later, what is FedRAMP's position on post quantum vulnerable cryptography? **Does FedRAMP consider this a vulnerability?**

## pete-gov (FedRAMP) — [2026-09-16T20:22:50Z](https://github.com/FedRAMP/community/discussions/174#discussioncomment-18471207)

Hey Rob - [Executive Order 14112 Securing the Nation Against Advanced Cryptographic Attacks](https://www.federalregister.gov/documents/2026/06/25/2026-12909/securing-the-nation-against-advanced-cryptographic-attacks) established direction for the government's transition to post-quantum cryptography. Section 6 (Procurement) includes direction for coordinating efforts on the migration of cloud-based technologies to PQC and assigns work for NIST and the FAR Council related to updating the CMVP and updating acquisition regulations to require specific cryptographic implementations.

FedRAMP, like cloud service providers and the rest of government, is standing by for guidance based on the outcome of these tasks assigned to other parts of the government. More importantly, the Executive Order anticipates updated acquisition regulations that would apply to all covered systems to establish opinionated requirements. FedRAMP likely will not need to play any role in this, nor will we need to change any rules for FedRAMP Certification, because cloud services will have contractual requirements to follow that are outside the scope of FedRAMP.

> Given the acceleration of Post Quantum Computers and the risks associated with harvest and decrypt later, what is FedRAMP's position on post quantum vulnerable cryptography? Does FedRAMP consider this a vulnerability?

Not at this time - FedRAMP will follow whatever guidance CISA releases on this topic.

> My argument is that PQC vulnerable libraries should be considered a vulnerability and patched. 

I am unaware of any quantum-resistant libraries that are patched upstream versions of existing CMVP-validated libraries. My understanding is that a migration to a different algorithm with different implementations are required. In theory, if there's a patched upstream version of a currently CMVP-validated cryptographic module then yup, you can use it under FR's rules.

> There are currently no FIPS approved PQC libraries. Will FedRAMP allow the use of libraries that are in-process so we can begin the transition?

FedRAMP Class D Certified cloud service offerings are required to only use NIST CMVP validated cryptographic modules or their upstream versions to protect federal customer data - this allows individual agencies to determine if they wish to use cloud services that conform entirely to FIPS 140-3 or if they wish to log a waiver for the use of cloud services that patch security vulnerabilities. 

No agency has come to FedRAMP to request waivers for use of non-CMVP-validated PQC libraries in cloud services yet, but FedRAMP would be open to allowing that after consulting with CISA and NIST.

> As an advisor to multiple major security focused cloud service providers, the industry needs clear direction from the Government to kick off the transition to Quantum secure cryptography. 

The Executive Order directs a number of agencies and programs to provide this direction with clear timelines for each step... As those responsible parties hit those deadlines and release that guidance you can expect FedRAMP to begin incorporating it. The next big update will probably be to some rules in the Cryptographic Module Use ruleset to align with CISA's upcoming guidance on cryptographic bills of materials.

> **pete-gov (FedRAMP)** — [2026-09-24T22:42:45Z](https://github.com/FedRAMP/community/discussions/174#discussioncomment-18588032)
>
> Note that the crypto policy you linked is legacy - CR26 version is here: https://www.fedramp.gov/2026/reference/cryptographic-module-use/
> 
> > We've heard from Bouncy Castle that the 2.2 release is the upstream version of the current 2.0 that is currently certified. Would this constitute an "update stream" even though its adding additional algorithms in addition to the existing algorithms?
> 
> I think I see the contortion you are trying to make here and please, no. :) A cryptographic module is a set of things including cryptographic algorithms. When that module is validated, the algorithms are validated. An upstream release of that module that includes updates of the same algorithms and key generation is an upstream version of the approved cryptographic module - but new algorithms in that upstream release would not be upstream versions of approved cryptographic modules. It's just random new code that's never been validated added in on the side, not a patched version of validated software. You can use the updated 2.2 versions of the parts of the module validated in 2.0, but not the random new stuff that was never validated.
> 
> For example:
> 
> - CRYSTALS-Kyber (KEM) is not part of the [Bouncy Castle 2.0 CMVP validated cryptographic module](https://csrc.nist.gov/projects/cryptographic-module-validation-program/certificate/4743). This algorithm appears in Bouncy Castle 2.2, but would not be considered an upstream version of a CMVP validated cryptographic module.
> 
> - AES-KWP is part of the Bouncy Castle 2.0 CMVP validated cryptographic module. An upstream version of this algorithm exists in Bouncy Castle 2.2. If you use AES-KWP in Bouncy Castle 2.2, you are using an upstream version of a CMVP validated cryptographic module.
